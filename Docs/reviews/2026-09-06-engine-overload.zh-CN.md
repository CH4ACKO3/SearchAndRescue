# 无图形运行与超负荷救援评估（2026-09-06）

本轮建立了可用的无图形引擎评估入口，完成 6 路原版压力测试、3 个有图形对照和 2 个 CE 场景。默认调度权重保持不变，正常游戏进程与存档未被重启或修改。

## 无图形故障

旧日志首个异常发生在 `GlobalTextureAtlasManager.TryInsertStatic` 读取 `texture.width`：Null 图形设备下传入纹理为空。移除全部第三方内容的测试配置也会遇到依赖纹理的 UI 初始化，因此现有证据不足以归因于 DDS 优化。此次没有修改或回退 DDS 文件。

新增 `EngineBenchmarkHeadless`，在 Mod 构造阶段、Def.PostLoad 之前安装测试专用渲染适配，覆盖图集插入/烘焙、地形图标裁剪、OnGUI 和地图绘制分支。只在同时指定 `-sar-bench-worker -nographics` 时启用。实际 tick、地图维护、寻路、医疗与伤情计算继续使用引擎流程。启动阶段 Unity 仍会报告 Null 设备不支持 shader；实际加载与评估错误保留并使测试失败。

种子 701、702、705 使用字节相同的初始存档比较有图形/无图形模式，存活人数、药耗和错误数一致。702 的治疗轮数相差 1，完成时间相差 5730 tick；705 完成时间相差 750 tick。结果说明这些样本的生存结果一致，尚不能认定逐 tick 等价。评分保留重复基线，后续兼容模组也需要对照。

## 压力协议

默认生成器 `stress-v1`：4–5 医生、0–4 搬运者、28–40 患者，多处四肢割伤及 0.55–0.88 初始失血，有限药物。所有患者生成时存活，死亡来自真实引擎中的后续伤情变化。

压力场景固定观察到 24000 tick，首例死亡后继续运行。患者死亡、存活且仍需治疗、存活且已完成治疗分别计数。常规 `routine-v1` 保留完成后结束的协议和超时保护。

评分先比较整组救活人数，次级项包括完成治疗比例、失血负担、首次治疗等待、完成时间、药耗、换医和移动。整组多救活一人的收益高于全部次级项上限。逐场退步和最差存活率需要一并审阅。

基线重复运行的存活人数全部一致；六场首例死亡发生在 2730–6870 tick，全部继续观察到 24000 tick。6 路冷运行约 23 秒一批，热运行约 16–18 秒一批，单 worker 工作集约 1 GB。启动器默认并发从 2 增至 6，可配置到 12；尚未测定 12 路是否提高吞吐。

这次执行了 4 个 trial，仍处于 TPE 启动采样阶段；包括重复、确认及保留场景，共 40 次搜索评估。候选在训练场景救活 131/204，基线为 125/204；保留场景均救活 36/68。候选在种子 708 从 15 人降至 13 人，与 707 的提升抵消。因此只记录候选，正式默认参数保持原样。

## 兼容配置与验证

第一层扩展为 Core + Harmony + CE + SAR，重新生成独立模板。种子 801 存活 15/28、802 存活 11/34，均完整观察 24000 tick，运行错误和治疗所有权冲突为 0。这验证了 CE 配置的无图形压力评估流程；它与原版使用不同模板，不能用两者原始分数评价模组优劣。

最终完整运行文件复测原版 701/702 与 CE 801/802，存活人数保持一致。初次校准运行时未复制 Orders UI XML 和两个未启用的 MI XML 补丁；它们未参与这些自动救援场景。现有运行时与 `New-EngineProfile.ps1` 均包含 Patches、LoadFolders.xml 和其他完整运行文件，并输出文件哈希清单。

有效性验证：

- Release 编译：0 警告、0 错误；76 项生产规则、9 项连续性、40 个调度场景及 200 个随机图检查通过。
- `routine-v1` 的 600 tick 超时及完整治疗后结束均通过。
- 故意将 CE 存档交给纯原版 worker，会在实际读档前拒绝模组列表不一致。
- Python 编译、PowerShell 语法、独立配置生成及文件清单检查通过。

首次创建模板时，RimWorld 自动启用了尚未登记的 DLC，导致配置不一致；该批次未产生有效评分，已排除。配置工具现会登记官方 DLC 为已知内容，且 worker 严格核对存档/进程模组列表。

## 后续范围

可继续扩大原版场景和重复次数，再逐层加入 MI、护理、选药等兼容配置。感染、特殊器材、机械体、延迟伤员、更多地图结构仍需专门生成器。当前首次干预统计来自 Tend 回调，药耗为药品净减少量，移动为采样位移；生存主指标完整保留，这些次级统计仍有明确的覆盖范围。
