# Dead Man's Switch 与 Search and Rescue 兼容审计（RimWorld 1.6）

日期：2026-09-06

## 结论

本机所装 DMS Core、Synthetic、AncientCorps 和 Joint Operations 的机兵种族沿用原版 `BaseMechanoid` 数据链。它们的最终 `fleshType` 是 `Mechanoid`，`RaceProperties.IsMechanoid` 为真，并继承 `CompMechRepairable` 与机械能量需求。SAR 把玩家派系且具备能量需求与维修组件的这些单位识别为机械患者，自动维修调度遵守自动维修开关；不应把 Synthetic 当作有机人形使用药物、输血、CPR 或其他高级生物干预。

作为救援者时，DMS 的普通 Work 模式具有标准 `JobGiver_Work` 分支，SAR 能沿用原版机械体工作许可。实际能力仍由种族的 `mechEnabledWorkTypes` 决定：Core 的 `DMS_Mech_Lady` 同时有 Doctor 和 Hauling，Synthetic 的 `DMS_Mech_Maiden` 源码声明 Doctor，本轮最终 Def 还具有 Hauling，`DMS_Mech_Armiman` 有 Hauling，`DMS_Mech_BigSister` 两者都没有。Joint Operations 的 `DMS_Mech_Tinker` 只有 Construction 与 Smithing，因此不会成为 SAR 医生或搬运救援者；它自己的战地维修继续由原模组 WorkGiver 负责。

静态审计发现两个维修 JobDef 此前没有进入 SAR 的患者任务所有权目录：Framework 的 `FFF_RepairMech_Overseer` 与 Joint Operations 的 `Tinker_RepairAutomatroid`。本轮已将二者注册为 `Treatment`，以避免它们和 SAR 对同一机械患者重复派工。Tinker 的 `PRT_Mod.WorkGivers.WorkGiver_RepairAutomatroid_Smithing.HasJobOnThing` 也已加入计划边界门控，使它在 SAR 已持有治疗所有权时、Job 尚未生成之前就避让。原版 `RepairMech` 已经注册。

## 种族与维修接口证据

Core 的抽象 `BaseAutomatroidRace` 位于工坊根 `3121742525/1.6/Defs/Things_race/Races_Automatroid_Base.xml:24`，其父级为原版 `BaseMechanoid`。原版 `Data/Core/Defs/ThingDefs_Races/Races_Mechanoid.xml:4` 定义 `BaseMechanoid`，其中 `:25` 指定 `fleshType=Mechanoid`，`:46-52` 添加 `CompProperties_OverseerSubject` 与 `CompProperties_MechRepairable`。DMS 的派生种族没有覆盖 `fleshType`，所以不是仅靠名称推断，而是确定继承这些数据。

原版反编译 `work/decompiled-rw16/Verse/RaceProperties.cs:338` 将 `IsMechanoid` 定义为 `FleshType == FleshTypeDefOf.Mechanoid`。因此下列代表种族都满足 `IsMechanoid=true`：

|---|---|---|
| Core | `DMS_Mech_Lady` | Doctor、Hauling；`3121742525/1.6/Defs/Things_race/Races_Synthroid.xml:5,69-77` |
| Core | `DMS_Mech_Dogge` | 与 Lady 同文件 |
| Synthetic | `DMS_Mech_Maiden` | Doctor；`3374615241/1.6/Defs/Races_Maiden.xml:6,72-84` |
| Synthetic | `DMS_Mech_Armiman` | Hauling；`3374615241/1.6/Defs/Races_Armiman.xml:78,111-119` |

AncientCorps 的 `BaseAncientAutomatroidRace` 继续继承 Core 的 `BaseAutomatroidRace`。已核对的具体 raceDefName 为 `DMS_Mech_Gorod`、`DMS_Mech_Krepost`、`DMS_Mech_Molot`、`DMS_Mech_Pravda`、`DMS_Mech_Tsvetnik`、`DMS_Mech_Zabor`、`DMS_Mech_Zabor_Pirate`，文件位于 `3469398006/1.6/Defs/ThingDef_Race/Races_Automatroid_*.xml`。

Joint Operations 已核对的 raceDefName 包括 `DMS_Mech_AdvancedGeochelone`、`DMS_Mech_AdvancedGeocheloneBeta`、`DMS_Mech_QuietusEye`、`DMS_Mech_Tinker`、`DMS_Mech_Dandelion`、`DMS_Mech_Obsidian`、`DMS_Mech_Ranger`、`DMS_Mech_IronCurtain`、`DMS_Mech_Skullcracker`、`DMS_Mech_CarettaHeavy`、`DMS_Mech_CarettaRocket`，定义集中在 `3636378753/Defs/DeadManSwitch/DMSMechs.xml`。`DMSMechCorps.xml` 还定义军团 PawnKind/种族变体；它们沿同一 DMS 机械体继承链。

Framework 的反编译类型 `Fortified.ArtificialOrganism` 默认 `Repairable => false`，Framework 自己的 Overseer 维修逻辑会明确跳过这种对象。当前已核对 DMS 种族实际使用 `Fortified.WeaponUsableMech`、`Fortified.HumanlikeMech` 或 `Pawn`，没有使用 `ArtificialOrganism` / `ArtificialOrganismHumanlike`，所以该限制不会排除上述 DMS/Synthetic 代表。SAR 仍以确定接口 `IsMechanoid`、机械能量 need 和 `CompMechRepairable` 判断，而不依赖 Framework 的类型名。

## SAR 调度行为

`Source/SearchAndRescue/Compatibility/MechanicalCare.cs` 要求机械患者属于玩家派系、存活、`IsMechanoid`、有 energy need 和 `CompMechRepairable`。真正进入维修还要求 `autoRepair=true` 且 `MechRepairUtility.CanRepair`。这与 DMS 继承的接口一致；测试场景必须显式开启患者的自动维修开关。

`3121742525/1.6/Defs/Misc/ThinkTree_Mech.xml` 与 `ThinkTree_Lady.xml` 的 Work 模式均包含 allowed-area/energy 前置节点及普通 `JobGiver_Work`。`MechWorkerCompatibility` 因而允许仍有 Overseer、控制组设为 Work、能量充足且未休眠/充电/被玩家命令占用的 DMS 机兵参加 SAR。Dead Man's Switch 被触发后，Framework 的 `CompDeadManSwitch.Wake()` 会移除 Overseer 关系；SAR 此时拒绝它作为救援者，符合“脱离控制后自主行动”的 DMS 语义。它仍可走 Framework 自己的自修逻辑。

玩家派系的 DMS 机械体不满足 SAR Capture 的“倒地且敌对”条件。它们可作为救援或维修患者，但不是俘获接管目标。敌对/停用机兵的接管、黑入与复活由 Framework 的 `FFF_ControlMech_Overseer`、`FFF_HackDeactivatedMech`、`FFF_ResurrectMech` 处理。`Building_DeactivatedMech` 与 `Building_MechCapsule` 是 Building/IThingHolder 流程，不是 Pawn 患者；SAR 的救援/俘获不应替代这些接口。

Framework 的 `FFF_RepairMech_Overseer` 和原版 `RepairMech` 最终都调用 `MechRepairUtility`。Joint Operations 的 `Tinker_RepairAutomatroid` 使用 `PRT_Mod.Jobs.JobDriver_RepairAutomatroid`，其 WorkGiver `Tinker_RepairAutomatroid_Construction` 属 Construction。SAR 不会主动派 Tinker 做这项专用维修；注册 Treatment 所有权后，原模组一旦派出它，SAR 会为同一患者让路。

MobileDragoon 的 `DMS_LastPilot` 在 `3377130226/1.6/Defs/Pawnkinds.xml` 中使用 `race=Human`；外骨骼/弹射器不是新增机器人 race。Motorized 定义 `Vehicles.VehicleDef`（如 `DMS_ArmySteed_APC`、`DMS_Chameleon_TD`、`DMS_Chelydridae_MainBattleTank`、`DMS_Mule_ATV`），不属于 Pawn 医疗与 SAR 搬运范围。

## 本轮实现的诊断与所有权修复

新增 Debug Action：`Search and Rescue > Build persistent DMS compatibility fixture`，源码为 `Source/SearchAndRescue/Diagnostics/DmsCompatibilityDiagnostics.cs`。它分别生成并保留：

- 人类机械师；
- Core `DMS_Mech_Lady`；
- Synthetic `DMS_Mech_Maiden`；
- Joint Operations `DMS_Mech_Tinker`；
- 一名受伤、麻醉的人类伤员。

Action 会最多尝试 40 次，生成 Smithing 与 SAR Field Rescue 均可用且 `MechanicalCare.CanRepairWork` 为真的机械师。两个测试人类使用 `NameTriple`，避免后续亲属生成代码把人名强制转换为 `NameTriple` 时异常；机械体仍可使用 `NameSingle`。Action 优先把 Lady 放入机械师的 Work 控制组，再仅加入剩余带宽容纳得下的机械体；因此基础 6 带宽不足以覆盖三者时，实际维修患者仍处于 `ControlledPawns`。它开启自动维修和 SAR Field Rescue，并按种族许可设置 Doctor/Hauling。每个 Pawn 的生成都有独立异常边界；缺少一个 Def 不会阻止其余项目。日志打印 race、flesh、IsMechanoid、维修 comp、autoRepair、机械患者、需要维修、Capture 是否接受、Doctor/Hauling、SAR 开关、Work mode 和当前调度可用性。

Start Action 还给 Lady 添加 `SAR_Treat`，调用 `SearchAndRescueCoordinator.TryIssueJob(Treat)` 并要求机械师实际取得目标为 Lady 的原版 `RepairMech`。推进若干 tick 后运行 `Search and Rescue > Finish persistent DMS repair check`，会验证机械伤害低于 Start 时的基线；Finish 不清理 Pawn 或 designation。`Search and Rescue > Retry DMS managed repair` 可复用地图中已有 Lady；若旧机械师不能维修，它会生成合格替代者、在带宽内重绑现有 DMS 测试机械体并重试实际派工，不会再次生成整套 fixture。另有一次性敌对 Lady 检查：生成敌对机械体、添加原版 `Anesthetic` 使其倒地，断言 `TargetEligibility.CanBeCaptured` 与 Capture designator 都拒绝后立即销毁，避免用“己方且站立”这个较弱条件证明机械体排除。

另有 `Search and Rescue > Start DMS responder treatment` 与对应 Finish。它复用已受控、Work 模式且有 Doctor 许可的 `DMS_Mech_Maiden` / `DMS_Mech_Lady` 和人类测试伤员，移除旧的可护理伤势后添加稳定 `Bruise`，避免 CE 的失血稳定分支；随后按调度图的实际 pending assignment，以 `FollowupTreat` 和该机械体的 Paramedic provider 请求任务，接受 Lady 或 Maiden 中合法获胜的一方并启动原版 `TendPatient`。Finish 要求该 Bruise 已护理或已消退且治疗 Job 已结束，并记录实际 winner，从而覆盖 DMS/Synthetic 作为真实 SAR 医生的执行路径。

`Source/SearchAndRescue/Compatibility/DmsCompatibility.cs` 保存两个专用 JobDef 名及 Tinker WorkGiver 类型；`CompatibilityRegistry.cs` 分别按 `AOBA.Framework` 与 `DMS.Proton.JointOperations` 激活，将 `FFF_RepairMech_Overseer`、`Tinker_RepairAutomatroid` 注册为 Treatment，并门控 Tinker 的 `HasJobOnThing(Pawn, Thing, bool)`。反编译证据位于临时审计输出 `PRT_Mod.WorkGivers/WorkGiver_RepairAutomatroid_Smithing.cs:49-99`：目标 `t` 被转换成 Pawn，且必须同派系、存活、`IsMechanoid`、已征召、非自身、受伤并可达/可预留；`:102-111` 用该目标创建 `Tinker_RepairAutomatroid`。Action 同时打印 `RepairMech` 和这两个 JobDef 的实际所有权角色。

`dotnet build Source/SearchAndRescue/SearchAndRescue.csproj -c Release` 已通过，0 个警告、0 个错误。

## 25 模组组合已观察到的上游 Def 问题

组合存档 `SAR_CE_DMS_00_Base_20260906` 使用四个 DLC（不含 Anomaly）、CE、FFF、Exosuit Framework、Vehicle Framework、DMS 六个主/子模块、Paniel/Androids 与 More Injuries。加载未出现 exception，但实机日志已观察到以下 DMS/CE Def 警告：

- 三个 DMS PawnKind 的 `weaponMoney` 下限低于 CE 候选武器价格：Krepost 为 `9030 > 7230`、Tarbosaurus Railgun 为 `6760 > 5860`、Laser 为 `6845 > 5945`。Joint Operations 对应预算可见 `3636378753/Defs/DeadManSwitch/DMSMechCorps.xml:1103,1385,1431`；AncientCorps 的 Krepost PawnKind 预算还可见 `3469398006/1.6/Defs/ThingDef_Race/Races_Automatroid_Krepost.xml:311`。这是 DMS PawnKind/CE 武器池的上游配置问题，不是 SAR 调度异常。
- `Explosion_Small` 与 `Pawn_Melee_Punch_HitBuilding` SoundDef 缺失。Joint Operations 直接引用前者的位置包括 `3636378753/Defs/DeadManSwitch/DMS_Sledgehammer_Ammo.xml:84,155` 与 `DMS_RocketNest_Ammo.xml:96`。本轮未在所选 1.6 DMS 文件中定位后一个引用的最终来源；它仍按组合加载日志记录为待上游定位的问题。

## 已验证与待实测边界

本轮实机确认 Lady、Maiden、Tinker 的患者识别与三个维修 Job 的所有权登记。最终 1200 tick 的 SAR 原生 RepairMech 把 Lady 损伤从 10 降到 2；Lady 随后被调度为医护，完成了人类 Bruise 的原生 TendPatient。倒地敌对 Lady 的俘虏排除检查通过。最终存档重载后再运行 600 tick，没有新增游戏错误。见 [实机报告](2026-09-06-ce-dms-runtime.zh-CN.md) 和 [验证数据](../validation/2026-09-06-ce-dms.json)。

仍待专项验证：Maiden 独立完成治疗、Tinker/Framework 维修 Driver 在并发竞争中的完整执行与释放、觉醒过程中的资格变化、失活机体和胶囊的接管流程，以及各车辆/外骨骼与其他附属包的组合。Tinker 在本测试场景中因带宽不足保持未受控；报告没有把它的实际维修算作通过。
