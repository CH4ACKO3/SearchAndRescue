# 大规模组合的性能热点追踪

基于 `231fefc` 的 SAR 本体，增加独立测试模组的调用计时、返回结果计数、重建调用栈和失效分派样本。此轮目标是定位上轮的大规模性能回退，未调整生产调度策略。

## 场景和口径

同一初始存档：40 医生、32 搬运者、272 患者，AllTending，17 个单人睡眠位。游戏进程串行运行，Smart Speed 不限速。保存后的睡眠位、预约及工作分布由运行时快照再次核对。

A 轮比较完整模式与全部简化，约 1500 tick，每 300 tick 输出一次累计计时。B 轮观察约 900 tick，逐项恢复一个开关。C 轮增加要求重建的调用栈；D/F 轮抽取清理阶段的失效分派。各轮插桩不同，时间不作跨轮直接比较；短观察窗也不用于判断救治收益。帧边界存在少量 tick 超出。

嵌套计时不能相加：例如找床包含在目的地查询中，目的地查询又包含在候选评分和统一匹配中。LINQ 查询构造时间不代表枚举耗时；BuildSupplyTasks 的 MoveNext 已单独计时。所有窗口，包括初期高峰，都保留在本报告的数据中。

## A 轮：实际消耗在哪里

| 指标 | 完整模式（1548 tick） | 全部简化（1525 tick） |
| --- | ---: | ---: |
| SAR MapComponentTick 平均 | 16.13 ms/tick | 74.45 ms/tick |
| 全局及请求触发的重建总数 | 142 | 475 |
| 救援目的地查询累计耗时 | 7.48 s | 59.17 s |
| 补给可达性查询累计耗时 | 8.60 s | 39.46 s |
| 补给可达性查询次数 | 242285 | 924516 |

组合模式各窗口的 SAR 耗时约为 108.86、210.77、46.14、6.25、4.50 ms/tick。高峰集中在前半段，之后明显缓解。第 300～600 tick 之间新增约 290 次重建，接近每 tick 重建一次；平均值掩盖了这种集中卡顿。

主要调用链：

1. `MapComponentTick → RebuildPendingAssignments → MatchRescuePatients → BestStageChoiceCore → EdgeWeight → TryFindRescueDestinationCached → FindBestRescueBed`。
2. `ScheduleTransportAndStandbyAssignments → BuildSupplyTasks.MoveNext → SupplyMedicineAlternatives 的实际枚举 → SupplyReachableByAvailableHauler → WorkerCandidates/资格与可达性检查`。

组合模式的普通治疗选项选择仅约 0.63 s，已经远低于上述两个热点。搬运匹配求解本身也较小。继续削减普通选药或匹配求解精度，无法直接解决当前主要开销。

## B 轮：找床失败与开关组合

前 300 tick，组合模式实际找床 122178 次，只有 437 次成功，121741 次失败，失败率约 99.64%。失败后又调用了 243482 次替代床搜索，全部返回空。该阶段 `FindBestRescueBed` 耗时约 23.29 s。

现有目的地缓存只在一次调度重建内按“工作者、患者”复用。快速分配在近处候选均不可行时会继续扩大搜索；床位全被预约时，扩大的候选仍会失败。下一次重建清空缓存后，同一批负结果再次计算。

| 从全部简化中恢复的项目 | 观察 tick | SAR ms/tick | 重建次数 |
| --- | ---: | ---: | ---: |
| 完整模式基线 | 931 | 24.43 | 123 |
| 不恢复（全部简化） | 911 | 96.33 | 348 |
| 恢复完整救援分配 | 927 | 11.43 | 65 |
| 恢复完整搬运协调 | 908 | 22.70 | 103 |
| 恢复完整选药 | 909 | 134.16 | 436 |
| 恢复批量备药 | 911 | 100.47 | 329 |
| 恢复提前接手 | 911 | 117.32 | 413 |

这支持优先检查快速救援与简化搬运共同改变的分派过程。表中结果是单一存档、短窗口的消融观察，不代表普遍的独立开关收益，也不证明某一选项单独必然导致问题。

## C 轮：床位与重建来源

组合模式第 300、604 tick 的快照均为：17 个床位，17 个被预约，0 个已躺入伤员，同时有 17 个 Rescue 作业。床位已被在途搬运占用，并非地图上完全没有床。完整模式对应窗口没有床位预约。

到第 604 tick，重建请求中：

- `CleanupInvalidPendingWorkers` 发起了 296 次延迟为 0 的请求；其中第 300～604 tick 新增 248 次。
- `TryIssueJob → TryIssuePendingResponderJob → TryWakePendingWorker` 发起了 390 次延迟为 15 的请求。
- `UpdateActiveAssignments` 发起了 40 次延迟为 0 的请求。

因此存在“分派产生 → 执行或下一 tick 校验失败 → 清理 → 立即全局重建”的反馈循环。它同时放大找床负查询和补给候选的重复扫描。

## 失效分派的具体原因

F 轮共抽取 385 条清理阶段的失效样本，全部为 Supply，患者均已有 `active=Rescue`，且 `emergency=True`。例如同一工作者和患者在连续多个 tick 被重复分派，资源仍有 21 份、只需 4 份，取药预约检查为 True。

代码边界不一致：

- `BuildSupplyTasks` 排除了正在取药、用药治疗和已有补给物流的患者，但没有排除已有 Rescue 主任务的患者；这类患者在搬运者尚未接触时仍 Spawned，也仍可被判断为需要治疗。
- `PendingAssignmentValid` 只允许给没有主任务的患者，或满足条件的无药治疗患者并发送补给；已有 Rescue 的患者被 `!activeByTarget.ContainsKey(...)` 拒绝。
- 下一 tick 的 `CleanupInvalidPendingWorkers` 删除分派并以 delayTicks=0 要求重建，下一轮又生成相同类别的任务。

现有 `DebugPendingInvalidReason` 没有说明这项主任务占用检查，所以这些样本打印为 unknown；缺少异常日志并不代表分派正常。

这种不一致存在于公共任务生成/验证代码。实验性组合更容易把场景带入此状态，不应把问题简单归为某个匹配算法算得慢。

## G 轮：测试过滤的因果验证

保持全部简化开启，仅在测试模组的 TransportTaskEdgeWeight 前过滤“Supply 患者已有 Rescue 主任务”的候选，使其无法生成分派。该条件本来就会被正式代码的执行前验证拒绝。F/G 都启用返回值、调用栈和失效样本采集；G 另有测试过滤的反射开销。

| 指标 | F：原行为 | G：测试过滤 |
| --- | ---: | ---: |
| 实际观察 tick | 600 | 637 |
| SAR 平均耗时 | 176.46 ms/tick | 14.69 ms/tick |
| 重建次数 | 372 | 52 |
| 清理阶段失效分派样本 | 385 | 0 |
| 实际找床调用 | 304959 | 21954 |
| 找床耗时 | 58.24 s | 3.94 s |
| 补给可达性调用 | 737100 | 69556 |
| 补给可达性耗时 | 33.01 s | 2.62 s |

这是对重建反馈循环的因果验证，支持先修候选生成/验收不一致。两窗长度略有差异，诊断时间也包含插桩，不能把约 92% 的单场景耗时下降当作所有玩家的性能承诺。此过滤只在测试副本中，尚未合入 SAR 本体；后续正式修复仍需覆盖治疗、搬运、特殊医疗和无床位的行为回归。

## 后续优化顺序

1. 先统一补给任务生成与执行前验证的患者状态边界，消除反复产生、立即失效的分派。覆盖正在搬运、其它主任务占用，以及没有紧急需求的无药治疗，补齐失效原因说明。避免先用较长的全局间隔掩盖问题，以免拖慢真正的新急症。
2. 为失败找床减少重复计算。优先考虑可用床位/预约状态的索引和明确失效条件；床位新增、释放预约、患者类型及工作者权限变化都需要使相关结果重新可见。已有单轮缓存不能跨过密集重建。
3. 在一轮补给任务构造内复用合格、可用的搬运者候选，分离工作者资格、工作者到患者的可达性和物资取用检查，减少“患者 × 物资 × 全地图 pawn”重复筛选。最终预约、医疗限制和特殊模组条件继续实际校验。

验证下一步修改时，应同时比较重建次数、失败找床次数、补给扫描次数及有效分派，不以降低 TPS 压力或减少实际救援工作量作为唯一成功标准。

原始 CSV、调用栈、状态快照、程序集散列和汇总保存在 `Docs/validation/2026-09-13-large-hotspots/`。诊断脚本使用 `Run-CoordinationProbe.ps1 -HotspotPlan ... -HotspotTicks ... -TraceDirty`，格式见探针 README。

E 轮尝试 300 tick 时，被现有引擎基准的最小 600 tick 校验拒绝；未产生有效测量，不纳入结论。测试入口已增加对应范围及 30 tick 整数倍校验，随后使用 F 轮继续验证。
